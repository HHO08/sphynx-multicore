# المرحلة 1 — المواصفة المعمارية لجسر `extcores` (libretro host داخل PPSSPP)

**الحالة:** مسودة معمارية — تنتظر موافقتك على القرارات الأربعة في تقرير الجدوى.
**القاعدة الحاكمة:** لا سطر واحد يُعدَّل في `Core/`, `GPU/`, `HLE/`, `UI/` الأصلية. كل الكود الجديد يعيش في `extcores/`.

---

## 1) لماذا "host" وليس "دمج"؟

PPSSPP لا يعرف شيئاً عن libretro. الكورات المتاحة (melonDS, mGBA, Flycast…) تتحدث لغة `retro_*` فقط:
`retro_init()`, `retro_load_game()`, `retro_run()`, `retro_set_video_refresh()`, `retro_set_environment()` … إلخ.

إذن العمل الحقيقي هو كتابة الطبقة التي:

| الوحدة | مسؤوليتها | ما تُترجمه |
|---|---|---|
| `host/Loader` | `dlopen("libretro_<core>.so")` + قراءة `retro_get_system_info()` | نظام → ملف Core |
| `host/EnvCB` | تنفيذ `retro_environment()` | 60+ استعلاماً (نسيج، بكسل فورمت، core options، حفظ/تحميل، Rumble، Geolocation…) |
| `host/Content` | تحميل ملف اللعبة + التحقق من الامتداد | مسار ملف → `retro_game_info` |
| `video/GL` | نسيج GLES مقاس `retro_game_geometry` | إطار RGB565/0RGB1555/XRGB8888 → نسيج → رسم بإطار PPSSPP |
| `audio/Out` | OpenSL/AAudio بتردد الـ Core | `int16 stereo` → طابور صوت PPSSPP نفسه |
| `input/Pad` | قراءة حالة الأزرار من طبقة إدخال PPSSPP | PAD_* → `RETRO_DEVICE_ID_JOYPAD_*` |
| `detect/Table` | تحديد النظام من الامتداد + بصمة الرأس | مسار → `SystemId` |
| `settings/Bridge` | ترجمة `core options` إلى عناصر إعدادات بأسلوب PPSSPP | `retro_variable` ↔ `SettingInfo` |
| `ipc/Client` | قناة مع عملية الـ Core | أوامر/إطارات عبر ذاكرة مشتركة |

**القيود التي يجب أن يُصمَّم حولها:**
1. `retro_run()` دالة **حاجزة ومتزامنة** — لا تصلح أن تُستدعى من خيط الواجهة. تحتاج خيط محاكاة خاصاً + قفل إطارات.
2. `retro_set_video_refresh` يُستدعى من داخل خيط الـ Core؛ أي رسم من داخله على سياق GLES الخاص بـ PPSSPP يتطلب نفس السياق/نفس الخيط.
3. `retro_environment(RETRO_ENVIRONMENT_SET_PIXEL_FORMAT)` يقرر فورمت الإطار — يجب أن يُثبَّت **قبل** أول إطار.
4. الكورات التي تستخدم GLES مباشرة (melonDS, Flycast, Beetle PSX HW, N64) تحتاج **سياقاً منفصلاً** ولذلك يُستحسن أن تكون في العملية المنفصلة من البداية.

## 2) نموذج العزل (الجزء الأهم)

```
┌──────────────────────────── عملية PPSSPP الرئيسية ────────────────────────────┐
│  Core/ (PSP)  ─── غير ملموس                                                  │
│  UI/ (قائمة الألعاب، الإعدادات، الرسائل)  ─── غير ملموس                      │
│  extcores/ui  ─── إضافة أسطر قليلة جداً: تسجيل الأنظمة + فتح اللعبة          │
│  extcores/host ─── عميل فقط: يرسل أوامر، يستقبل إطارات/صوت                  │
└───────────────────────────────────┬──────────────────────────────────────────┘
                                    │  Binder/ASHMEM أو socket محلي
┌───────────────────────────────────▼──────────────────────────────────────────┐
│  عملية :extcore  (android:process=":extcore")                                │
│  libretro_<core>.so + حلقة retro_run + GLES خاص بها + صوت خاص               │
│  إذا انهارت: تُقتل هذه العملية فقط ← الواجهة و PSP continue                   │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **Watchdog**: إن لم يصل إطار جديد خلال 3 ثوانٍ → يُقتل الـ Core، وتُعرض رسالة بأسلوب PPSSPP: «تعذّر تشغيل هذا النظام — الـ Core توقف عن الاستجابة».
- **الذاكرة المشتركة**: نسيج مزدوج التخزين المؤقت (double-buffered) + حلقة صوت بحجم 60 م.ث.
- **بلا شبكة**: لا صلاحيات جديدة، ولا اتصال بالإنترنت من هذه الطبقة إطلاقاً.

**التكلفة الحقيقية لهذا القرار:** IPC يضيف زمن نسخ إطار واحد (≈ 1–4 م.ث على 1080p). على الأجهزة الضعيفة هذا مقبول مقابل ضمان عدم انهيار التطبيق. الكورات الخفيفة جداً (NES/GB/GBA) يمكن أن تعمل لاحقاً داخل نفس العملية كتحسين أداء اختياري — بموافقتك.

## 3) الكشف التلقائي (البند 7 من رسالتك)

الترتيب الإلزامي، و**PSP أولاً دائماً**:

| # | القاعدة | مثال |
|---|---|---|
| 1 | `.iso/.cso/.pbp/.elf/.prx` + مسار PSP → **Core الـ PSP الأصلية** (لا يُستشار أي جدول خارجي) | أي لعبة PSP |
| 2 | امتداد حصري لنظام واحد | `.nes`, `.gb`, `.gba`, `.md`, `.sfc`, `.gdi`, `.chd`+`.gdi` مجاور |
| 3 | امتداد مشترك → قراءة أول 512 بايت (magic) | `.bin/.cue` → PSX vs SegaCD vs PCE-CD |
| 4 | ما زال غامضاً → **قائمة PPSSPP نفسها تعرض سؤالاً بأسلوبها**، مرة واحدة، ويُحفظ الجواب لكل ملف | `.iso` غير PSP |

هذا يحقق «لا تدخل يدوي» عملياً في 95% من الحالات، ولا يكذب عليك في الـ5% الباقية (التباس حقيقي لا يمكن حسمه رياضياً).

## 4) إعدادات الـ Core بشكل PPSSPP (البند 7 الحاسم)

الطريقة التي تحفظ الشكل الأصلي 100%:

1. لا تُنشئ شاشة جديدة. **سجّل خيارات الـ Core في نظام `SettingInfo` الموجود في PPSSPP** كإعدادات ديناميكية تُقرأ عند فتح الإعدادات أثناء تشغيل لعبة خارجية.
2. تظهر داخل **نفس** أقسام PPSSPP: Graphics / Audio / Controls / System — بنفس الخط والألوان والترتيب، لأنها فعلياً نفس القائمة.
3. كل عنصر يحمل وصفاً قصيراً من الـ Core (`retro_get_core_option`) بشكل tooltip بأسلوب PPSSPP.
4. خيارات الـ Core تُخزَّن في `extcores.ini` داخل مجلد PPSSPP نفسه، محفوظة لكل نظام.
5. «Save State / Load State» تُربط بـ `retro_serialize()` وتُخزَّن بنفس مجلد وعنونة حالة PSP للألعاب الخارجية.

**ما لا يمكن تحقيقه:** كل خيار في كل Core. الهدف المُعلن: 8–12 خياراً لكل نظام تغطي ما يستخدمه اللاعب فعلاً (دقة، سرعة، صوت، إطارات، تحكم).

## 5) ترتيب التنفيذ داخل المرحلة 1 (إثبات جدوى صغير جداً)

الهدف: **Gambatte (GB/GBC) فقط** يعمل، لأنه أصغر Core (≈ 0.7 م.ب) وأبسط متطلبات (لا BIOS، فورمت إطار بسيط).

1. `extcores/host/Loader` + `EnvCB` الحد الأدنى (16 استعلامًا).
2. `video/GL` + `audio/Out` + `input/Pad` بأبسط شكل.
3. زر «فتح ملف» مؤقت (خارج الواجهة النهائية) لتشغيل `.gb`.
4. اختبار انحدار PSP: تشغيل لعبة PSP قبل وبعد — يجب أن يكون السلوك مطابقاً بايت ببايت في الأداء.
5. قياس: زمن الإطار، استهلاك الذاكرة، حجم الـ `.so`.

عند نجاح ذلك، تتكرر نفس الدورة لكل Core بنفس القالب — ولهذا يجب أن تكون الواجهة (`host/`) عامة تماماً ولا تحتوي أي شيء خاص بأي نظام.
